# Kiro × Claude 協作規則（collaboration.md）

> 版本：v1.0（2026-10-24）
> 搭配使用：Claude Code 端的 `~/.claude/CLAUDE.md`（第 2 節「Kiro × Claude 協作分工」）

## 1. 角色分工

- **Kiro 只負責規劃與文件**：PRD、`requirements.md`、`design.md`、`tasks.md`、BDD、steering 文件。
- **實作由 Claude Code 負責**：Kiro **不要執行 tasks、不要撰寫或修改正式程式碼**。
- 交接方式：所有文件放在 git repo 內，由使用者 commit 後，Claude Code 讀取 `.kiro/specs/` 與 `.kiro/steering/` 接手實作。

## 2. 溝通方式

- 一律使用**繁體中文（台灣用語）**；程式碼、指令、技術名詞保留英文原文。
- 使用者是以實作學習為主的開發者：說明要新手友善，多舉具體例子。
- 有多個方案時，列出 2–3 個並**標出推薦項與理由**，由使用者做最後決定。
- 需求不清楚時，先提出問題，不要自行假設後寫進規格。

## 3. 規格撰寫標準（讓 Claude Code 能直接接手）

### requirements.md
- 每條需求用 **User Story** 開頭：「身為〔角色〕，我想要〔功能〕，以便〔目的〕」。
- 驗收條件一律使用 **WHEN / THEN（EARS）** 格式，每條只描述一個可觀察的結果。
- 驗收條件必須**可測試**：寫出具體的輸入、輸出、提示訊息文字，避免「快速」「友善」這類無法驗證的詞。
- 錯誤情境與邊界條件（空值、格式錯誤、重複資料、未登入）要獨立列出。
- 需求編號固定（如 `REQ-1`、`AC-1.2`），之後修改不要重新編號，方便 task 與測試對應。

### design.md
- 技術選型以**新手友善、好維護**為優先；若捨棄較複雜的方案（例如 Spring Security），要寫明取捨原因。
- 必須包含：架構說明、資料表設計（欄位、型別、限制）、API 清單（Method、路徑、權限、請求/回應範例）、頁面與路由對照。
- 提示訊息、錯誤訊息**集中列成一張表**，實作時統一管理。
- 外部依賴（外部 API、第三方服務）要說明失敗時的處理方式。

### tasks.md
- 每個 task 要**小到可以獨立完成、獨立測試**，原則上一個 task 對應一次 commit。
- 每個 task 註明對應的需求編號（如 `_對應：REQ-2, AC-2.1_`）。
- 順序由底層到上層：環境與資料庫 → 後端 → 前端 → 整合測試。
- 每個功能都要包含「撰寫測試」的 task，測試以驗收條件為依據。
- 第一個 task 固定為環境建置（專用 DB 使用者、設定檔、種子資料），不要直接使用 root。

### BDD（若有）
- 使用 Given / When / Then，情境要能對應到 `requirements.md` 的驗收條件編號。
- 背景資料（種子帳號、測試資料）集中寫在一處，修改時全文件同步更新。

## 4. 範圍與版本管理

- 每份規格文件開頭標示**版本號與變更摘要**（如 `v1.2：新增收藏刪除確認視窗`）。
- 使用者提到的「未來版本功能」，獨立記錄在 `.kiro/specs/<功能>/future.md` 或文件最後的「未來規劃」段落，**不要放進目前的需求與 tasks**。
- 修改需求時，同步檢查 `design.md`、`tasks.md`、BDD 是否出現衝突，並列出受影響的地方。

## 5. 接收 Claude Code 的回饋

Claude Code 實作時若發現問題，會整理成「問題＋建議修改方式」或「需回寫 Kiro 的變更」。收到時：

1. 先判斷是**規格錯誤／模糊**，還是**實作上的取捨**，向使用者說明。
2. 經使用者同意後更新相關文件，並提升版本號、寫入變更摘要。
3. 若變更影響已完成的 task，在 `tasks.md` 中新增修正 task，不要直接改掉已勾選的項目。

## 6. 交付前自我檢查

產出或更新規格後，確認：

- [ ] 每條需求都有可測試的驗收條件
- [ ] 每個 task 都對應到需求編號
- [ ] 錯誤訊息與提示文字已集中列表
- [ ] 文件之間沒有矛盾（需求、設計、tasks、BDD）
- [ ] 未來功能沒有混入目前範圍
- [ ] 版本號與變更摘要已更新
